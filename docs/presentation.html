New Product Development — Case Study

Syntaxin

The problem was never that health data is dirty. It's that every system speaks a different syntax — going in and coming out — and that integration cost is what stops tools from scaling.
Syntaxin solves two problems, and uses AI at each:
  • I/O — standardize the boundary in both directions: any source → canonical, and canonical → any target system's API.
  • Application — conduct data-agnostic analysis on the canonical model.
The canonical model is the fixed contract between them. Demonstrated on a high-value clinical use case: abnormal-result triage + care-gap over Annual-Wellness-Visit panels.

Problem 1 — I/O · standardize input & output variation

Map arbitrary syntax ↔ the canonical model, both directions

Input — any export → canonical

  • AI proposes a mapping spec (data, not code) from samples → human reviews → fixed engine applies
  • Trusted / repaired / gated: each result carries its own reference range (trusted); BP "150/99" text, ragged rows, sentinels → repaired & logged; impossible values → gated out
  • Verified lossless (coverage + round-trip) — renamed-column, re-delimited copy → identical output

Output — canonical → a target's API

  • AI reads the target's API doc → induces a field-map (spec, not code) → deterministic client
  • Human-gated dry-run — a real write is an approved action
  • The mirror of input: same mechanism, reversed
Same move in and out: AI compiles heterogeneous syntax into governed, reviewed mapping specs — and never authors the artifact that executes. The messy-data judgment lives here, at the input boundary.

Problem 2 — Application · data-agnostic analysis

Analyze the canonical model — agnostic to source, aware of content

Deterministic clinical work

  • Abnormal-result triage — plausibility gate: Sodium 178 → critical vs Sodium 208 · SpO₂ 126% → impossible, diverted
  • Care-gap — expected test never-ordered vs ordered-but-unresulted (the open loop)
  • 1,288 results → 25 critical · 128 care gaps · 25 impossible diverted

Where AI does real work

  • Suggests what to analyze — data-aware, from schema + single-signal findings (pairwise → dominant-set cliques; recovered Glucose ↔ HbA1c)
  • Reasons over unstructured notes → cited Assessment / Plan, verified against governed rules
Agnostic to form (any schema), aware of content (an analysis runs only if its entities are present) — data-agnostic, never data-blind.

The safety contract — and the risks it contains

AI at every edge — never in the action

Fact vs. hypothesis

  • Facts are deterministic & authoritative — values, ranges, severities, rules
  • The LLM is advisory, cited, verified — never emits a value, rule, URL, or action; a verifier rejects unsourced content (it caught its own false-positives)
  • Human approval gates the write, not the reading

Biggest risks & mitigations

  • Generic stats ≠ clinical judgment → two tiers (stats for data-quality, governed rules for clinical)
  • Med-recon false positives (dose parsing, brand≡generic) → verified pipeline found the truth: 0 real gaps. Honest > inflated.
  • Out-of-scope data → fail safe; correlation ≠ causation → cliques are candidates, human-validated
Across both problems, AI sits at the edges — mapping in, mapping out, suggesting & reasoning in the middle — while the executable artifact and the action stay governed and human-gated. That is the ethos of Syntaxin.

Appendix · A2 — research avenue

Scaling the analysis tier without exploding

Single-signal analysis is a no-brainer. For k-uplets (joining k signals), the space of combinations is a power set — you can't enumerate it.
k=1 single-signal analyzers run (free, immediate) → fast tickets schema + k=1 findings → what's possible × what's interesting k=2 pairwise affinity (|corr|, min co-observation) → O(N²), tractable graph → dominant sets (Pavan–Pelillo, replicator dynamics) → coherent, overlapping cliques cliques = candidate k-uplets → human-curated → governed analysis
Run on the real panel (npm run cliques): it recovered known physiology — Glucose ↔ HbA1c and a Sodium · Creatinine · Urine-ACR renal cluster — with no enumeration; a cohesion gate rejects the incoherent leftover.
  • Higher-order groups are discovered from pairwise structure, not brute-forced. Anticorrelation is as informative as correlation.
  • Cliques are hypotheses, not conclusions — correlation stays a candidate; governed rules + a human decide meaning. (Confounding, support, stratification all apply.)

Appendix · A3

Composable microservices — canonical model as the contract

POST /connect/discover schema discovery (LLM) + quick sample round-trip POST /connect/load full-dataset load + verify; manifest bypasses the LLM; a failed induced mapping is repaired — the specific failing fields are fed back to the model, not re-rolled blindly POST /analyze canonical dataset → registry of analyzers → tickets POST /publish tickets → target field-map → dry-run (human-gated)
  • Each stage is independently callable; the canonical model is the stable interface between them.
  • Isolating the output connector encodes the write-safety boundary — nothing reaches a chart except through the one human-gated endpoint.

Appendix · A4

Data-agnostic, not data-blind — and a governance spectrum

Agnostic input, aware analysis

  • Agnostic to form (any format/schema → canonical) — the connector.
  • Aware of content — an analyzer runs only if its entities are present; unknown data → clinical analyzers sit out, the generic one still runs.

Who decides an analysis runs

  • Human-authored requirements — fully governed
  • AI-suggested, human-validated — nothing runs unreviewed
  • Requirement-free (*) — generic, runs on anything
Autonomy in applicability never becomes autonomy in action — every result still flows through verify → tickets → human gate.

Appendix · A5 — where I/O goes next

An ingestion agent: read the schema, hold the credentials, close the loop

Today the input is a file drop. The same AI-reads-a-spec move extends one layer further — to autonomous, credentialed access to the source system itself.

Given a DB schema / API doc + credentials, the agent can

  • Collect — discover and pull the data from the source system
  • Push back — read the write API → know what to send and where
  • Analyze — the schema itself reveals which entities exist → which analyses are even possible

Why we didn't (yet)

  • No access to live systems; the data was provided as flat files
  • So we took the simpler route — drag-and-drop → connector. Same architecture; the agent just sits in front of it.
Same ethos, one layer up: AI reads a spec (schema / API doc), operates under governed credentials, and still never authors the action — collection, push, and analysis stay human-gated.
